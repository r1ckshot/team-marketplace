# Тести розрахунку: еталон, який справді щось тримає

Цей скіл існує через конкретну знахідку 2026-08-03 (F1, сценарій `zlecenie`):
свіжонаписаний набір тестів був зеленим, виглядав повним — і **пропускав три
навмисні поломки арифметики з п'яти**. Причина не в лінощах, а в двох звичках,
що виглядають нормальними: перевіряти попадання числа в смугу і формулювати
очікування як нерівність.

Тому порядок нижче не про «написати тести», а про **перевірити, що написані
тести падають, коли код неправильний**. Тест, який не падає на зламаному коді, —
не гарантія, а її імітація.

## Крок 1 — вивести еталон РУКАМИ

Порахуй очікуване число незалежно від реалізації: за формулою з
`docs/EVIDENCE.md`, у тому порядку дій, що в нормі закону.

- [ ] Формула взята з EVIDENCE, не з читання коду сценарію.
- [ ] Проміжні величини виписані (база, внески, витрати, податок), а не лише
      підсумок: саме вони підуть у назву тесту.
- [ ] Рахунок зроблено окремо (наприклад `node -e` з вписаними числами), **без
      виклику функції, яку перевіряєш**.

Якщо еталон розійшовся з реалізацією — спершу з'ясуй, хто правий, і назви
причину. Підправити тест, щоб зійшлось, — найшвидший спосіб зафіксувати баг
назавжди (`.claude/rules/testing.md`).

## Крок 2 — звіряти ЦЕНТР смуги, не попадання в неї

`toRange` віддає симетричну смугу ±4% (`UNCERTAINTY.ARITHMETIC`) — це продуктове
рішення «діапазони, не точні суми», а **не допуск для арифметики**. На 9,000 zł
смуга — це ±360 zł: помилка в 164 zł/міс сидить усередині й не помічається.

```ts
const exact = (r: { min: number; max: number }) => (r.min + r.max) / 2;
expect(exact(sub('kup20')!.rangeMonthly!)).toBeCloseTo(9045.03, 2);
```

- [ ] Кожен еталон — `toBeCloseTo(<число>, 2)` від центру смуги.
- [ ] `rangeContains` лишається тільки там, де перевіряється сама смуга
      (наприклад, що вона перетинається з калібрувальним діапазоном EVIDENCE).
- [ ] Арифметика виведення стоїть у **назві** тесту: `витрати 25,783.86 → дохід
      103,135.46 → PIT 8,776.25 → на руки 9,045.03`.

## Крок 3 — гілки, а не щасливий шлях

Окремий файл `app/lib/calc/__tests__/<slug>.test.ts`. Покривається кожна
розвилка, що змінює висновок:

- [ ] Кожна відповідь анкети, від якої залежить число (збіг титулів, добровільна
      складка, вид роботи).
- [ ] Кожна недоступність: `available: false` + правильний `unavailableReasonKey`.
- [ ] Кожен ліміт і поріг — **на обох боках межі**. Ліміт, що не перевіряється
      вище себе, не перевіряється взагалі: у F1 30-krotność при базовому профілі
      15,000 zł просто не вмикалась, тож її «покриття» було уявним.
- [ ] Примітки: `noteKeys` містить те, що людина мусить прочитати.

## Крок 4 — рядок у наскрізному UI-тесті

`app/components/__tests__/flow.test.tsx`: після проходу анкети новий сценарій
видно в таблиці, кількість рядків оновлена, ключова примітка на екрані.

⚠️ Пастка з F1: медіанний шлях **не відповідає** на питання, які показуються
умовно (`showIf`). Якщо сценарій спирається на таку відповідь, у тесті буде
значення за замовчуванням — і текст примітки не сміє приписувати людині вибір,
якого вона не робила.

## Крок 5 — мутаційна перевірка (крок, заради якого все це)

Зламай реалізацію навмисно й переконайся, що тест **падає**. Мінімум чотири
мутації, кожна — окремо, з відкатом:

| Що ламати | Чому саме це |
|---|---|
| База розрахунку (`X - Y` → `X`) | Найтихіша помилка: результат лишається правдоподібним |
| Ліміт/стеля (`Math.min(a, cap)` → `a`) | Спрацьовує лише на великих значеннях — легко не покрити |
| Умовна гілка (`cond ? a : b` → `a`) | Перевіряє, що гілка справді перевірена |
| Прапорець із відповіді (`answers.x && …` → `false`) | Ловить «тест дивиться не на те» |

```bash
cp app/lib/calc/scenarios/<slug>.ts /tmp/<slug>.bak
perl -0pi -e 's/<оригінал>/<мутація>/' app/lib/calc/scenarios/<slug>.ts
npx vitest run app/lib/calc/__tests__ | grep -E "^ +Tests"
cp /tmp/<slug>.bak app/lib/calc/scenarios/<slug>.ts
```

- [ ] Кожна мутація дала **червоне**. Зелена мутація = дірка в тестах, і
      закривається вона доти, доки не почне падати.
- [ ] Після останнього відкату повний прогін знову зелений (перевір, що бекап
      справді повернувся).

Звітуй числом: «4 з 4 мутацій спіймано», а не «тести покривають».

## Крок 6 — чесність про прогін

```
npx tsc --noEmit && npm test && npm run test:ui
```

Кажи фактом: «N node + M UI зелені». Якщо частина набору не ганялась — скажи
прямо, що саме і де його прогнати (`.claude/rules/testing.md`).
